# 污染场地障碍因子诊断的双轨建模与验证研究报告

## Executive summary

这项工作应被严格定义为**“障碍因子诊断”**，而不是“污染风险二分类预测”。也就是说，系统的核心输出不应只是“是否高风险”，而应是：**在某一修复后用途下，哪些因子正在构成主要障碍、其方向是什么、贡献有多大、解释是否稳定、证据链是否可审计**。你上传的整改方案已经明确把任务从“单一预测分数”纠偏为“规则底座 + 机器学习归因 + 因子排序 + 证据链”的结构，这个方向是对的，而且与高风险场景更需要可解释、可审计而非单纯追求 AUC 的主流观点一致。fileciteturn0file0 citeturn5academia2turn9view0

从建模角度看，你当前的数据形态是**污染场地监测大表**，包含重金属、有机与复合污染物的实测值，且业务要求按修复后用途拆成**生产轨**与**生态轨**。这意味着推荐默认采用**双轨独立建模**，而不是把所有用途硬塞进一个模型。独立模型更容易满足法规解释、阈值管理、审计留痕和验收展示；只有在两轨标签稀疏、样本重叠显著、且你能证明共享表征确有收益时，才建议尝试 multi-task 或 shared backbone + heads。对于中小规模表格数据，树模型仍是更稳妥的默认选项；深度模型只有在样本量更大、存在明显时序/图像/文本/遥感等多模态输入时才值得上。citeturn6academia0turn15academia0turn18academia3turn16academia0turn19view0turn16academia2

验收上最关键的不是“随机切分下 AUC 高不高”，而是**空间外推、场地外推、时间外推和来源外推是否仍成立**。因此本报告建议把验证主线改为：`GroupKFold / LeaveOneSiteOut / LeaveOneRegionOut / time-based split / source split`，并在所有预处理、阈值调优、校准、解释导出过程中坚持“外层测试集绝不泄露”。这不是形式主义，而是因为模型选择偏差、预处理泄露和小样本高方差会系统性抬高成绩。citeturn4view0turn4view2turn9view0turn7academia0turn12academia0

我建议你把项目落地成四层：**规则层**负责法规阈值与硬性红线；**建模层**负责双轨障碍排序与不确定性；**解释层**负责 SHAP/ALE/反事实的业务映射；**审计层**负责 dataset_version、model_version、feature_schema_hash、validation_strategy、SHAP snapshot、人工复核触发记录。最终甲方看到的不是“一个神秘 AI 分数”，而是一套可复现、可追责、可解释的诊断系统。fileciteturn0file0 citeturn5academia0turn38academia0turn20academia0turn37academia0turn36academia1

## 任务定义与业务边界

按你给定的验收口径，本项目的规则底座应以 **GB15618、GB36600、HJ25.5 及相关 HJ25.x 指南**为基础，但建模目标不是复写标准本身，而是回答：“**在某个修复后用途下，哪几个因素最妨碍场地达到目标状态**”。这一定义与你上传的整改方案一致：整改方案已经明确要求把“原始观测”“规则判断”“模型归因”拆开，避免把模型误包装成替代法规判断的黑箱。fileciteturn0file0

之所以必须做**生产/生态双轨**，是因为两类后用途的目标函数不同。生产轨通常更关注**作物安全、产能恢复、农艺约束、残留进入食物链的风险**；生态轨则更关注**生物可利用性、生态毒性、土壤生物活性、植被恢复、结构与功能恢复**。污染总量相同，并不意味着两条轨道的障碍因子排序应相同：例如某些金属在生产轨上主要通过食用安全阈值表现为障碍，而在生态轨上则更可能通过可利用性、pH、土壤有机质、微生物活性和植物建立失败体现为障碍。污染物“总量”与“有效暴露/有效危害”并不等价，这一原则在生物可利用性研究与土壤健康研究中是长期共识。citeturn40search0turn39search0turn35academia1turn44academia5

因此，**“同一块地、同一批检测值、两条轨道输出相同排序”反而应被视为可疑**。如果生产轨与生态轨长期输出完全一样，通常意味着标签构造、阈值继承、权重设计或特征工程没有真正体现用途差异，模型只是复写了同一个规则层。整改时应把这类现象列为红旗。fileciteturn0file0

## 数据与标签设计

训练数据建议分成两张逻辑表：第一张是**检测长表**，保留原始监测事实；第二张是**训练宽表**，服务模型输入。长表至少应包含以下字段：`site_id`、`sampling_event_id`、`sample_id`、`measurement_id`、`analyte_code`、`analyte_group`、`original_value_text`、`qualifier`、`detection_limit`、`value_used_for_model`、`unit`、`replicate_group_id`、`sample_depth`、`matrix_type`、`lab_id`、`method_code`、`data_origin`、`dataset_version`、`collected_at`、`import_batch_id`。其中 `original_value_text`、`qualifier`、`detection_limit` 用来保留检出限与未检出语义；`replicate_group_id` 用来避免平行样被静默平均；`data_origin` 用来区分 `real / literature / synthetic / demo`；`dataset_version` 用来锁定训练与报告的一致性。你上传的整改方案也已经强调，数据版本、来源与解释快照必须贯通。fileciteturn0file0

下面给出一个建议性的 SQL/ETL 骨架。它的目标不是把所有业务写死，而是把**“原值保留、替代值显式、规则与模型分层、版本可回放”**落到结构上。

```sql
-- 长表：保留原始检测事实
create table measurement_long (
  measurement_id         uuid primary key,
  site_id                uuid not null,
  sampling_event_id      uuid not null,
  sample_id              uuid not null,
  analyte_code           text not null,
  analyte_group          text,
  original_value_text    text,
  qualifier              text,         -- '<', '<=', 'ND', 'J', ...
  detection_limit        numeric,
  value_used_for_model   numeric,      -- 不覆盖 original_value_text
  unit                   text,
  replicate_group_id     text,
  sample_depth_cm        numeric,
  matrix_type            text,
  method_code            text,
  lab_id                 text,
  data_origin            text not null, -- real/literature/synthetic/demo
  dataset_version        text not null,
  collected_at           timestamp,
  imported_at            timestamp default now()
);

-- 轨道阈值/权重表：规则层与模型层共用基线
create table factor_rule (
  analyte_code           text not null,
  track                  text not null, -- production / ecology
  threshold_type         text not null, -- upper/lower/range
  threshold_value        numeric,
  threshold_low          numeric,
  threshold_high         numeric,
  weight                 numeric default 1.0,
  standard_code          text,
  standard_version       text,
  applicable_land_use    text,
  notes                  text
);

-- 宽表视图：场地-版本级输入
create materialized view feature_wide as
select
  site_id,
  dataset_version,
  max(region_code) as region_code,
  max(land_use_after_remediation) as land_use_after_remediation,
  percentile_cont(0.5) within group (order by case when analyte_code='PH' then value_used_for_model end) as ph,
  -- 典型 pivot，可按 analyte_code 动态生成
  max(case when analyte_code='CD' then value_used_for_model end) as cd,
  max(case when analyte_code='PB' then value_used_for_model end) as pb,
  max(case when analyte_code='AS' then value_used_for_model end) as arsenic
from measurement_long
where data_origin = 'real'
group by site_id, dataset_version;
```

标签设计上，不建议把任务压成一个“是否障碍”的单标签二分类，而更适合做**多标签障碍识别 + 因子排序**。一种实操方案是：对每个 analyte / 因子单独生成 `production` 与 `ecology` 两套标签，再组合为排序学习输入。最简单的 severity 可写成：

```python
severity = max(0, log2((value_used_for_model + eps) / (threshold + eps)))
weighted_severity = severity * factor_weight
```

但要注意：**如果标签本身直接由同一批浓度按同一阈值机械计算，而模型又把这些浓度原样作为特征，那么你不是在“预测”，而是在“重复规则”**。这并非完全无意义，但它改变了模型的职责：模型应主要承担**排序、交互修正、不确定性评估、缺失情形推断与人工复核优先级**，而不是冒充法规判断器。这个边界必须在模型卡里写清楚。fileciteturn0file0 citeturn5academia2turn37academia0

防止标签泄露时，我建议你把以下规则写成硬约束，而非“最佳实践建议”。第一，**先分训练/验证/测试，再做任何 imputation、scaling、feature selection、threshold tuning、calibration**；所有预处理都必须包进 Pipeline。第二，使用**按场地/区域/来源/时间的分组切分**，而不是随机切分。第三，若使用类别编码或目标统计编码，必须避免用目标泄露式编码；CatBoost 的 ordered boosting 正是为缓解这类 target leakage 而设计。第四，如果采用软标签或专家共识标签，label smoothing 只能作为辅助正则，不能替代脏标签治理。citeturn4view2turn4view0turn16academia2turn25academia0

建议把数据质量检查脚本做成 CI 中的一个独立 stage，至少检查以下内容：

```python
def validate_training_contract(df):
    required = [
        "site_id", "dataset_version", "original_value_text", "qualifier",
        "detection_limit", "replicate_group_id", "data_origin"
    ]
    missing = [c for c in required if c not in df.columns]
    assert not missing, f"missing columns: {missing}"

    assert set(df["data_origin"].dropna().unique()) <= {"real", "literature", "synthetic", "demo"}
    assert not ((df["data_origin"] != "real") & (df["dataset_version"].str.contains("official", case=False, na=False))).any()

    # 同一 replicate_group_id 不允许在 ETL 中被静默平均
    duplicated = df.groupby(["site_id", "dataset_version", "replicate_group_id"]).size().reset_index(name="n")
    assert (duplicated["n"] >= 1).all()

    # 检出限语义必须被保留
    censored = df["original_value_text"].astype(str).str.startswith("<") | df["qualifier"].astype(str).isin(["<", "ND", "未检出"])
    if censored.any():
        assert df.loc[censored, "detection_limit"].notna().all()
        assert df.loc[censored, "value_used_for_model"].notna().all()
```

## 模型与训练策略

在当前业务下，最稳妥的建模路线不是“一上来就找最强深度网络”，而是按下面的优先级推进。第一层是**规则基线**：完全依据 GB/HJ 与项目规则库生成候选障碍因子和 severity。第二层是**可解释监督模型基线**：如 logistic / EBM / 小型 GBDT，用来学习规则之外的交互和上下文。第三层是**树模型主力方案**：Random Forest、XGBoost、LightGBM、CatBoost。第四层才是**深度模型**：仅当你有明显的时序、多模态、大样本或跨站点迁移需求时启用。对于典型表格数据，树模型仍是更高性价比的默认项。citeturn5academia2turn16academia0turn19view0turn19view2turn6academia0

双轨训练策略我建议按以下准则决策。**默认：独立模型**。优点是法规解释最清晰、模型卡最容易写、阈值版本最容易锁定、演示时对甲方最直观。**可选：shared backbone + heads**。前提是两条轨采用相同的大部分输入特征，且你能证明共享层提升了数据效率或稳定性。**谨慎使用：multi-task GBDT / multi-task deep learning**。只有当两轨标签相关但不相同、样本重叠高、单轨标签稀疏时才值得尝试。换句话说，multi-task 不是“高级所以要上”，而是“有统计动机才上”。citeturn15academia0turn18academia3

验证策略必须从“随机 KFold”升级为“监管级分组验证”。`GroupKFold` 允许你确保同一组只出现在一个测试折中；这对于“同一场地不同采样深度”“同一场地不同批次导入”“同一机构同一来源的文献记录”尤其重要。环境建模里，leave-one-province-out / leave-one-city-out 往往比普通 CV 更能暴露真实外推误差；你的场景也应如此，至少应配置 `LeaveOneSiteOut`、`LeaveOneRegionOut`、`time-based split` 和 `source split` 四套验证。citeturn4view0turn12academia0turn9view0turn7academia0

阈值与概率也不能偷懒。若你输出的是“某因子成为障碍的概率”或“进入 top-k 的概率”，则默认 0.5 阈值几乎一定不合业务。阈值应在**内层验证**中按业务代价函数调优，例如更重视 `recall@k`、高风险漏判成本或人工复核负载，而不是测试时再手调。概率输出则应做校准，并把校准方式写入模型注册表。citeturn4view1turn22view0

一个实用的训练配置建议如下：

- **Random Forest**：做强鲁棒基线与特征稳定性对照。参数重点在 `max_features`、`min_samples_leaf`、`n_estimators`。citeturn6academia2
- **LightGBM**：做主力迭代模型，适合较大表和快速试错。重点调 `num_leaves`、`min_data_in_leaf`、`feature_fraction`、`bagging_fraction`、`lambda_l1/l2`。citeturn19view0
- **XGBoost**：做高强度基线与可控正则方案。重点调 `max_depth`、`eta`、`subsample`、`colsample_bytree`、`gamma`。citeturn16academia0turn19view1
- **CatBoost**：当存在机构、区域、土类、土地利用等类别特征时优先比较，因为其 ordered boosting 能显著降低类别处理中的泄露风险。citeturn16academia2turn19view2

## 泛化评估与可解释证据链

对于“障碍因子诊断”任务，AUC/F1 只能算**模型健康指标**，不能算核心交付指标。真正应该放在报告首页的是**因子排序稳定性**与**适用边界**。我建议主指标至少包括：`top-k precision`、`top-k recall`、`rank correlation (Kendall/Spearman)`、`coverage`、`calibration`、`SHAP consistency` 与 `人工复核触发率`。AUC/F1 仍然保留，但只能作为补充。这样做与你项目整改方案里“从单一分类转向因子排序与证据链”的方向一致。fileciteturn0file0 citeturn22view0turn24view0

实验矩阵建议覆盖五类情况。第一，**站点外推**：LeaveOneSiteOut。第二，**区域外推**：LeaveOneRegionOut。第三，**时间外推**：按采样时间先后切。第四，**来源外推**：按 `data_origin / source_id / DOI / project_batch` 切分。第五，**压力测试**：缺失值注入、测值噪声注入、异常极端浓度、合成样本扰动。凡是 synthetic/demo 数据，只能用于压力测试或方法学验证，禁止混入正式效果报告。citeturn12academia0turn23view0turn36academia0

统计检验建议一律带区间。对于 top-k 指标、rank correlation 和 calibration，可使用 bootstrap 生成 95% CI；对于两个模型、两轨方案或两种标签构造的差异，可用 permutation test 做非参数显著性比较。SciPy 已提供直接可用的实现。citeturn27view0turn27view1turn26view0

解释层建议采用“**树模型 SHAP 为主，LIME/IG/反事实/ALE 为辅**”的组合。原因很简单：SHAP 在树模型上成熟、速度快、输出可加总，适合形成**障碍因子贡献表**；ALE 在强相关特征下比 PDP 更稳健，适合解释 pH、有机质、CEC 与金属之间的依赖结构；LIME 可以作为对单一样本的轻量对照解释；反事实则适合生成“如果想让某因子不再进入 top-3，应改变什么”的行动建议。若未来确实上深度模型，再引入 Integrated Gradients。citeturn5academia0turn4view3turn20academia1turn21academia0turn20academia0turn38academia0

一个**可审计的障碍因子证据链**，至少应包含以下字段：

- `dataset_version`
- `training_dataset_version`
- `model_version`
- `validation_strategy`
- `group_key`
- `feature_schema_hash`
- `threshold_library_version`
- `rule_snapshot`
- `shap_snapshot_path`
- `top_k_factor_table`
- `confidence_interval_json`
- `ood_score`
- `human_review_triggered`
- `review_reason`

这里最重要的不是“多存几个字段”，而是让甲方或审计人员能回答四个问题：**用的是什么数据版本？按什么方式验证？这个因子为什么排第一？如果我今天重跑还能不能得到同样结果？** 模型卡和数据卡正是为这个目的而设计。citeturn37academia0turn36academia1

下面给出一个可复现的 Python 骨架，用于单轨模型训练与 SHAP 导出：

```python
from sklearn.model_selection import GroupKFold
from lightgbm import LGBMClassifier
import shap, json, numpy as np, pandas as pd

X = feature_df.drop(columns=["site_id", "dataset_version", "target"])
y = feature_df["target"]
groups = feature_df["site_id"]  # 或 region_code / source_id

cv = GroupKFold(n_splits=5)
fold_scores = []
models = []

for fold, (tr, te) in enumerate(cv.split(X, y, groups=groups), start=1):
    model = LGBMClassifier(
        n_estimators=300,
        learning_rate=0.03,
        num_leaves=31,
        subsample=0.8,
        colsample_bytree=0.8,
        random_state=42,
    )
    model.fit(X.iloc[tr], y.iloc[tr])
    prob = model.predict_proba(X.iloc[te])[:, 1]
    fold_scores.append({"fold": fold, "mean_prob": float(prob.mean())})
    models.append(model)

best_model = models[0]
explainer = shap.TreeExplainer(best_model)
shap_values = explainer.shap_values(X.iloc[:100])

np.save("artifacts/shap_snapshot.npy", shap_values)
with open("artifacts/model_card.json", "w", encoding="utf-8") as f:
    json.dump({
        "model_version": "obstacle_prod_v1",
        "dataset_version": "2026Q2_real_only",
        "validation_strategy": "GroupKFold(site_id)",
        "feature_schema_hash": "sha256:...",
    }, f, ensure_ascii=False, indent=2)
```

## 生产轨与生态轨差异化设计

生产轨标签的目标，不应只是一句“是否适合生产”，而应拆成更接近业务的几个子目标。最实用的三类是：**食安与残留风险**、**产能与农艺约束**、**修复后稳定利用的可持续性**。因此生产轨特征工程除了污染物浓度外，还应更重视 pH、CEC、有机质、盐分、有效态金属、典型作物敏感性、历史耕作/灌溉条件等。其障碍排序往往会把**残留风险高但也可通过管理缓解**的因子排在前面。citeturn35academia1turn44academia5turn16academia0

生态轨则不同。生态轨更像是在回答：**这块地能不能恢复成一个功能正常、毒性受控、植被与土壤生物可持续建立的生态系统？** 因此它应更强调生物可利用性、毒性敏感性、植物建立失败、土壤微生物/酶活性、结构稳定性、含水/团聚体与有机碳恢复。换句话说，生态轨对“总量高但不活跃”与“总量一般但高生物可利用性”的区分更敏感。citeturn40search0turn39search0turn29academia1turn35academia1

所以我建议在标签构造上直接把差异写进公式，而不是靠模型自己“悟出来”。例如：

```python
# 生产轨
prod_score = (
    0.45 * food_safety_severity +
    0.25 * crop_uptake_risk +
    0.20 * soil_fertility_constraint +
    0.10 * management_feasibility_penalty
)

# 生态轨
eco_score = (
    0.35 * bioavailable_toxicity +
    0.25 * vegetation_establishment_penalty +
    0.20 * microbial_function_penalty +
    0.20 * soil_structure_recovery_penalty
)
```

在因子级标签上，也建议使用**“因子-轨道二维标签”**而不是把所有因子映射到一条公共分数线上。例如：

```python
y_prod_cd = f(total_cd, pH, crop_type, threshold_GB15618, available_cd)
y_eco_cd  = g(available_cd, porewater_proxy, pH, SOM, eco_toxicity_proxy)

y_prod_pah = f(total_pah, edible_pathway, volatilization_proxy)
y_eco_pah  = g(bioavailability_proxy, vegetation_response, microbial_response)
```

这样设计后，“Cd 在生产轨是 top-1，但在生态轨是 top-4；有机质在生态轨是 top-2，但在生产轨靠后”才会变成一个**可解释且合理**的现象，而不是模型噪声。fileciteturn0file0

## CI/CD、部署与合规

建议你把模型治理直接并入 CI/CD，而不是等到验收前手工补。最少需要四个清单文件或表：`model_registry`、`dataset_registry`、`validation_runs`、`audit_packages`。其中 `model_registry` 必须包含：`model_id`、`model_version`、`training_dataset_version`、`feature_schema_hash`、`validation_strategy`、`group_key`、`threshold_library_version`、`ood_policy`、`human_review_policy`。这套字段与你想做的甲方验收相容，也与模型卡/数据卡的主流记录方式一致。citeturn37academia0turn36academia1

人工复核触发规则建议明确写成政策，而不是“感觉不稳时再看”。推荐触发条件如下：

- `OOD score` 超过阈值；
- top-1 与 top-2 障碍因子差值过小；
- 同一场地不同外层折 SHAP 排序不稳定；
- 关键输入缺失率高；
- 数据来源不是 `real`；
- 模型校准误差过大；
- 生产轨与生态轨结果异常一致。

若需要置信覆盖保证，可在输出层增加 conformal calibration；若需要异常监测，可配合 Isolation Forest / LOF 做新样本分布偏移检测。citeturn36academia0turn23view0turn22view0

报告展示时，我建议甲方界面固定显示四块信息，而不是只展示一句结论：

1. **验证方式**：例如 `GroupKFold(site_id) + LeaveOneRegionOut holdout`
2. **适用边界**：污染类型、地区、采样年代、数据来源
3. **当前结论**：双轨 top-k 障碍因子与置信区间
4. **审计证据**：数据版本、模型版本、规则版本、解释快照编号

这会极大降低“看起来像 AI 幻觉”的风险。citeturn37academia0turn36academia1
