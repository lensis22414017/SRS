## 摘要陈述（Summary Statement）

**整体推荐：Major Revisions（大改后再评审）**。

本系统作为 AI 代理协作生成的工程，**工程骨架完成度高**（34 条功能需求逐条映射、70 测试通过、五阶段闭环跑通、三层离线地图、报告图件、RAG 降级链），展现了远超"玩具项目"的成熟度。但存在 **1 项必须立即修正的数据真实性红线违规**、**1 项模型性能虚高风险**，以及若干 AI 生成代码的典型质量问题（异常吞没、N+1 查询、无错误边界）。这些问题不影响"主干能跑"，但直接影响"能否作为科学工程交付甲方并经得起审查"。

**关键优点**：
- 工程结构清晰，前后端分离，模块职责明确。
- 数据闭环设计严谨：split 双键（DOI+Source）零泄漏校验、合成数据标记隔离。
- 安全基线达标：无硬编码密钥、`.env` 未入库、密码哈希、RBAC 前后端双重拦截。

**关键弱点**：
- 🚨 `data/raw/真实数据集.csv` 被替换为模拟 F 特征表，模型版本号仍标"真实 n1119"，**冒充真实数据**。

- 异常吞没（11 处 `except Exception: # noqa`）掩盖潜在故障；前端无 ErrorBoundary。

## Major Comments（必须修正，影响交付有效性）

### Major 1：数据真实性红线违规（CRITICAL）

**问题**：`data/raw/真实数据集.csv` 当前是 **11690 行 × 136 列（F1_土壤容重 … F127）的模拟特征表**，但：
- 文件名仍叫"真实数据集"；
- `ml/models/data_prep.py:26` 硬编码 `DATA_VERSION = "真实数据集_20250731_n1119"`；
- 6 个已训练 RF 模型的 `data_version` 元数据全部标注"真实数据集_n1119"，但实际 `test_size=2338`（远超 1119），特征是 F1-F127（非 Cr/Hg/As/Pb 重金属）。

**为什么是问题**：同时违反 `AGENTS.md` 两条红线——①"raw 不可变"②"模拟不得冒充真实"。这是科学诚信底线，若甲方按模型元数据追溯会得到**完全错误的"真实性能"认知**。文档 `docs/algorithms/rf_shap.md:11` 仍宣称"1118 样本，重金属 Cr/Hg/As/Pb"，与实际训练数据完全不符。

**证据**（铁证）：
- 模型 AUC 演变：20260610-12 为 `auc=0.999 test_size=224`（真表时期），20260613-16 变为 `auc=1.000 test_size=2338`（换表后）——**数据置换的精确时点**。
- 当前 CSV：`ID` 唯一值=11690（完全唯一），标签 0:10420 / 1:1270，特征全是 F_中文物理量。

**建议**（项目组已选"正本清源改名+如实标注"）：
1. `真实数据集.csv` → 重命名为 `模拟特征表_F127_n11690.csv`；
2. `DATA_VERSION` 改为 `模拟特征表_n11690`，移除"真实"字样；
3. 模型元数据增加 `is_real_data: false` 标记；
4. 文档 `rf_shap.md` 同步修正训练集描述；
5. 评估报告如实标注"当前模型基于模拟特征表，AUC=1.0 为模拟数据虚高，真实数据模型待重建"。

### Major 2：RF 模型 AUC=1.0 的特征泄漏与虚高风险（CRITICAL）

**问题**：RF 模型在 11690×130 特征上 AUC=1.0、accuracy=1.0、f1=1.0。完美分两类可能：

1. **ID 列泄漏**：`ID`（1…11690 完全唯一）被作为特征输入（`feature_list` 含 `'ID'`）。RF 可学到"ID 在某区间→某标签"的伪规则，这是教科书级的泄漏。
2. **模拟数据的合成规则**：F1-F127 表本质是按规则生成的模拟数据，标签可能与特征存在确定性派生关系（如"风险等级"→"标签"），导致模型学到的是生成规则而非真实规律。

**为什么是问题**：AUC=1.0 在真实土壤数据上几乎不可能。`extreme_validation` 报 `keyword_hit_accuracy=1.0, quality=100` 会给甲方"模型完美"的错误印象，一旦部署到真实场地，性能必然骤降。

**建议**：
1. 训练前剔除 `ID` 列（唯一标识不应入特征）；
2. 在评估报告显著位置标注"模型性能基于模拟特征表，含 ID 列，AUC=1.0 为虚高，不可外推到真实场地"；
3. 长期：用 `merged_std33,zh .xlsx`（41504×719 真实文献数据，带 DOI/Source）重建模型，报告真实 AUC（预期 0.7-0.9）。

### Major 3：异常吞没掩盖故障（11 处）

**问题**：`except Exception: # noqa: BLE001` 共 11 处，多数用 `pass`/`continue` 静默吞掉异常：
- `report_service.py:113`（matplotlib 画图失败静默 → 报告无图但不报错，运维无感知）
- `report_service.py:425`（DOCX 嵌图失败 → "[地图图件渲染失败]" 但不记录原因）
- `launcher.py:262`（GUI 提示失败 → 仅终端打印，用户看不到阻断项）
- `download_admin_boundaries.py`（5 处，单文件下载失败静默跳过）

**为什么是问题**：生产环境故障会被静默吞掉，运维无法定位。AI 代码常见反模式——为"不崩溃"而过度防御，代价是丢失可观测性。

**建议**：所有 `except Exception` 至少 `logger.warning(f"... 失败: {e}")` 记录，关键路径（报告/启动）失败应上抛或显式降级提示。

### Major 4：前端无错误边界 + API 无统一错误拦截

**问题**：
- 前端无 `ErrorBoundary` 组件（React 组件抛错会整页白屏）；
- `api/client.ts` 无统一响应拦截器（无 `.catch` 统一处理），各页面散落 `try/catch`，错误体验不一致；
- 16 处 `loading=` 处理但无骨架屏（Skeleton），加载态粗糙。

**为什么是问题**：用户遇到网络抖动/后端 500 时，体验是"白屏"或"无反馈"，降低可交付感。

**建议**：加全局 `ErrorBoundary` + axios 响应拦截器统一 toast + 关键页面加 Skeleton。

## Minor Comments（应改进，提升质量）

### Minor 1：N+1 查询
`backend/app/api/system.py:49-63` 在循环里逐条查 User/Organization。场地列表、报告等列表接口存在同类问题。建议用 `joinedload` 或批量预取。

### Minor 2：同步阻塞 IO 在 API 线程
`import_service.py:93-94` 直接在请求线程 `pd.read_excel`。大文件（>50MB）会阻塞 worker。建议异步任务化（已有 `ingest_service` 雏形，未接线）。

### Minor 3：TODO/FIXME 残留 17 处
grep 显示 17 处 `TODO/临时/暂时/placeholder`。生产交付前应清零或转为 issue 跟踪。

### Minor 4：测试覆盖缺口
18 个测试文件 / 40 个源模块，`audit_service`、`ingest_service` 无测试。关键路径（审计日志、导入队列）缺回归保护。

### Minor 5：文档与代码漂移
`SRS.md` 称训练集"1118 样本 + 重金属 Cr/Hg/As/Pb"，实际已变 11690 F 特征表。`rf_shap.md` 同样过时。文档需随数据修复同步（CLAUDE.md §16 已要求）。

### Minor 6：launcher 超时硬编码
`launcher.py` 启动自检的 Redis 探测 `socket_connect_timeout=1.5` 硬编码，弱网环境可能误报。建议参数化。

### Minor 7：前端主包体积
`dist/assets/*.js` 主包 2.5MB（无路由级懒加载）。首屏加载偏慢，应做 `React.lazy` 分包。

## 方法学严谨性评估（Stage 3）

### 统计与机器学习
- ❌ **过拟合未防范**：AUC=1.0，ID 列泄漏，无交叉验证报告（只有单次 train/test）。
- ⚠️ **类别不平衡**：标签 0:1 = 10420:1270（约 8:1），未见 SMOTE/class_weight 配置，AUC=1.0 可能掩盖少数类问题。
- ✅ **分组划分正确**：split 用 `connected_components(DOI,Source)`，避免同文献跨集泄漏——这是亮点。
- ⚠️ **评估指标单一**：只报 accuracy/f1/auc，无 PR-AUC、校准曲线、混淆矩阵，少数类表现不可见。

### 实验设计
- ✅ **合成数据隔离**：`is_synthetic` 标记贯穿 model_ready/split，`synthetic_not_in_real` 校验通过。
- ⚠️ **外部验证集**：`external_literature_holdout` 存在但未见在评估中独立使用，泛化能力未验证。
- ❌ **模型对比缺失**：SRS.md 提"RF/SVM 五模型对比"，但 artifacts 只有 RF，未见对比记录。

## AI 生成代码质量专项（补充维度）

作为 AI 代理协作产物，本系统呈现典型的"AI 代码优点与通病并存"：

### 优点
- **结构化强**：模块分层清晰，命名一致，几乎无重复代码（EDA 图件构造函数复用度高）。
- **防御性意识**：边界态（空数据/无坐标/无 key/模型失败）几乎都有处理与降级。
- **文档意识**：关键函数有 docstring，参数有 `_source`/`_note` 说明。

### 通病
- **过度防御 = 静默吞错**：11 处 `except Exception: # noqa`，AI 倾向"别让它崩"，牺牲了可观测性（Major 3）。
- **"看起来对就行"**：AUC=1.0 未被质疑（Major 2），AI 满足于"测试通过"而非"结果可信"。
- **命名继承债务**：数据被换但文件名/版本号未同步（Major 1），AI 不主动审查跨文件一致性。
- **性能意识弱**：N+1、同步阻塞 IO（Minor 1/2），AI 优先功能正确性，性能优化需人提示。
- **前端工程化浅**：无 ErrorBoundary/无统一错误拦截（Major 4），AI 对前端最佳实践覆盖不足。
